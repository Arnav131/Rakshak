# Rakshak — Setup & Usage Instructions

This is a step-by-step guide to get the Rakshak Railway Maintenance Dashboard running
locally, from a clean machine to seeded demo data. A full **feature catalog** is below so
reviewers can see everything the product does and exactly where to try it.

---

## Feature Catalog (What Rakshak Can Do)

### 1. Operations Dashboard — `/`
The command center home page, rendered live from the database (no mock data):
- KPI cards (active alerts, open tickets, sensors online, track sections monitored)
- Top 5 critical/warning alert feed
- Track section health breakdown derived from real alert aggregates
- Sensor trend charts (Chart.js) and recent sensor readings table
- System summary doughnut chart and operator activity log
- Live clock and animated KPI counters

### 2. Interactive Railway Map — `/map/`
Leaflet.js dark-themed map of the rail network:
- Station markers with health status color-coding
- Track polylines from real `TrackSection` geometry
- Active alerts and open tickets overlaid on the map
- Summary stats bar (stations, routes, alerts, tickets counts)
- Simulated train markers moving along routes in real time (`train_simulation.js`)
- Click-through popups linking to alerts/tickets detail

### 3. Alert Management — `/alerts/`
- Full alert list with severity badges (critical / warning / caution / info)
- Filtering by severity (`?severity=`) and by status
- Alerts are auto-generated by the AI pipeline when anomalies are detected
- Alert escalation tracking and acknowledgment workflow

### 4. Ticket Management — `/tickets/`
- Maintenance ticket board with priority and status filtering (`?status=`)
- Live search endpoint (`/tickets/api/search/`)
- Tickets linked to assets/track sections with maintenance team assignment
- Status change logging (`TicketStatusLog`) for accountability

### 5. Live AI Simulation — `/simulation/` *(staff/admin only)*
Answers "where is the live input?" — generates fresh data on every run, never preloaded:
1. Pick any source and destination station (120+ seeded stations)
2. Real shortest-path routing: Dijkstra over actual track sections in the DB
3. An LLM generates a brand-new synthetic 16-reading IoT journey for that route
   (fallback chain: Gemini → Grok → Anthropic → OpenAI → Ollama → physics-based RNG,
   so it works even with zero API keys configured)
4. All 16 readings are streamed through the REAL production prediction pipeline
5. UI plays a pixel-art train animation + terminal-style log, then renders the verdict:
   alert level, fault type, anomaly score chart, and actionable suggestions
6. Automatically opens/updates an Operational Readiness clearance case for that exact route

### 6. AI Prediction Engine (the core of Rakshak)
A trained multi-model inference pipeline loaded from `ai_engin/trained_models/`:
| Model                | File                      | Purpose                                                                                                  |
| -------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------- |
| VAE anomaly detector | `vae_anomaly_detector.pt` | Deep-learning detection of abnormal sensor patterns                                                      |
| Failure predictor    | `failure_predictor.pt`    | Future failure risk at 1h / 6h / 24h horizons                                                            |
| Fault classifier     | `fault_classifier.pt`     | Classifies fault type (rail fracture, thermal buckle, gauge widening, ballast washout, subgrade failure) |
| Isolation Forest     | `isolation_forest.joblib` | Classical ML anomaly detector                                                                            |
| Statistical detector | `stat_detector.joblib`    | Fast statistical deviation checks                                                                        |
| Meta-classifier      | `meta_classifier.joblib`  | Fuses scores from all detectors into one verdict                                                         |

- Uses a 64-reading rolling window per sensor (sequence model)
- Monitors 4 physical signals: ambient temperature, humidity, vibration RMS, gauge width
- Centralized severity thresholds keep alert severities and ticket priorities consistent
- Predictions automatically create Django `Alert` records for operator follow-up
- Graceful rule-based fallback layer when models/deps are unavailable

### 7. Operational Readiness Control Center — `/readiness/`
Departure-clearance workflow for routes/train services:
- Case dashboard with Ready / Conditionally Ready / Hold summary counters
- Per-case safety checklist (route health, signal interlocking, schedule window…)
- Field sign-off per checklist item with role designation and notes
- Controller decision submission (ready / conditionally ready / not ready)
- Telemetry evaluation: case metrics auto-refresh from live/simulated sensor data
- Full audit trail (`ReadinessAuditRecord`) of every action

### 8. Worker Patrol & Review — `/patrol/` and `/patrol/admin/`
Human field-inspection loop that complements the AI:
- Workers submit patrol reports against real track sections, rating 8 categories:
  Rail Condition, Track Geometry, Sleepers & Fastenings, Ballast Condition, Drainage,
  Points & Crossings, Level Crossings, Formation & Earthwork
- Personal patrol history for workers; staff can preview all reports
- Admin review dashboard: weighted scoring, category weight adjustment, and final decision
- Role-gated: `patrol_worker` group sees the worker page, staff see the review console

### 9. Authentication & Roles
- Login/logout (Django auth) with role badge in the UI
- **Controller (staff)** — full access incl. Live Simulation
- **Patrol Worker** group — patrol submission access
- **Read-only viewer** — dashboards without control actions
- Server-side enforcement on every restricted page and API (not just hidden menus)

### 10. REST JSON APIs
Map & ops data: `/api/stations/`, `/api/routes/`, `/api/alerts/`, `/api/tickets/`,
`/api/summary/`, `/api/trains/`
Predictions: `/api/predict/`, `/api/predict/batch/`, `/api/predict/health/`
AI subsystem: `/api/ai/predict/`, `/api/ai/predict/batch/`, `/api/ai/health/`, `/api/ai/providers/`
Simulation: `/api/simulation/run/`, `/api/simulation/stations/`, `/api/simulation/route/?from=NDLS&to=CSMT`
Readiness: `/api/readiness/cases/`, sign-off & decision endpoints
Patrol: start/list/detail/ratings/weights/decision endpoints under `/api/patrol/`

## Judge Quick Demo Script (5 minutes)

1. Log in as a staff user → land on **Dashboard**: point out KPIs, charts, alert feed.
2. Open **Map** → show network, click a station/alert popup, watch trains move.
3. Open **Alerts** and **Tickets** → filter by severity/status.
4. Go to **Simulation** (staff-only): pick two stations, press Run → watch the train,
   terminal log, then the AI verdict + suggestions. Note it generated fresh LLM telemetry
   and ran it through the real model pipeline.
5. Follow the readiness link from the result into **Operational Readiness** → sign off a
   checklist item and submit a controller decision.
6. Open **Patrol** → show the 8-category inspection form; then **Patrol Admin** review.
7. Optionally hit `/api/ai/health/` to show the live model registry status.

## 1. Prerequisites

Install the following before starting:

- **Python 3.10 or above** — https://www.python.org/downloads/
  (check "Add Python to PATH" on Windows during install)
- **Git** — https://git-scm.com/
- **A Supabase account** with an active project — https://supabase.com/
- **pip** (bundled with Python)

Verify your installation:

```bash
python --version   # should print 3.10+
git --version
pip --version
```

---

## 2. Clone the Repository

```bash
git clone https://github.com/<your-username>/<repository-name>.git
cd <repository-name>
```

All Django commands in this guide are run from inside `backend/`.

---

## 3. Create a Virtual Environment

### Windows

```bash
python -m venv .venv
.venv\Scripts\activate
```

### Linux / macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
```

You should see `(.venv)` at the start of your terminal prompt.

---

## 4. Install Dependencies

The AI prediction feature is core, not optional. Install the full ML stack:

```bash
pip install -r requirements.txt
```

This includes Django, the PostgreSQL driver, NumPy, PyTorch, and scikit-learn so the
local pickle-based prediction pipeline loads correctly. Installation may take several
minutes because of PyTorch.

> Colab-only training dependencies live separately in `notebooks/requirements-colab.txt`.

---

## 5. Get Your Supabase Database URL

1. Open your project on https://supabase.com/.
2. Click **Connect** in the top bar.
3. Copy the **Session pooler** connection string (it works on IPv4 networks; port `5432`).
4. It looks like:
   ```
   postgresql://postgres.<PROJECT_REF>:<PASSWORD>@aws-0-<REGION>.pooler.supabase.com:5432/postgres?sslmode=require
   ```
5. Replace `<PROJECT_REF>` and `<PASSWORD>` with your actual values.

> SQLite is intentionally disabled. If `DATABASE_URL` is missing or points to SQLite,
> Django raises a setup error before startup.

---

## 6. Configure Environment Variables

Copy the template and edit it:

```bash
# Windows
copy .env.example .env

# Linux / macOS
cp .env.example .env
```

Edit `.env` and set at minimum:

```env
DEBUG=True
SECRET_KEY=change-me-in-production
ALLOWED_HOSTS=127.0.0.1,localhost
DATABASE_URL=postgresql://postgres.<PROJECT_REF>:<PASSWORD>@aws-0-<REGION>.pooler.supabase.com:5432/postgres?sslmode=require
```

Optional — AI scenario generation for the Simulation page (fallback order:
Gemini → Grok → Anthropic → OpenAI → Ollama → Physics RNG). Add any one of these keys;
the system falls back automatically if one fails or is missing:

```env
GEMINI_API_KEY=your-gemini-api-key-here      # https://aistudio.google.com/
GROK_API_KEY=xai-your-key-here               # https://console.x.ai/
ANTHROPIC_API_KEY=your-key-here              # https://console.anthropic.com/
OPENAI_API_KEY=sk-your-key-here              # https://platform.openai.com/
```

**Never commit `.env` to git.**

---

## 7. Apply Migrations

From the repository root:

```bash
cd backend
python manage.py migrate
```

Expected output: a series of `Applying railway.XXXX... OK` lines.

---

## 8. Seed Demo Data

Run these commands **in order**, still from `backend/`:

```bash
python manage.py seed_master_data   # zones, divisions, 120+ stations
python manage.py seed_routes        # ~400 track sections + geometry
python manage.py seed_sensors       # sensor types, sensors, readings
python manage.py seed_demo_data     # alerts, tickets, maintenance teams
python manage.py seed_users         # user accounts (incl. staff users for Simulation)
```

No manual database setup is needed after this.

---

## 9. Run the Development Server

```bash
python manage.py runserver
```

Open **http://127.0.0.1:8000/** in your browser.

`seed_users` creates three ready-made logins for demos:

| Username     | Password    | Role                   | Access                                                                            |
| ------------ | ----------- | ---------------------- | --------------------------------------------------------------------------------- |
| `controller` | `admin123`  | Controller (superuser) | Everything, incl. `/simulation/`, `/patrol/admin/`, and Django admin at `/admin/` |

### Creating your own staff account

```bash
cd backend
python manage.py createsuperuser
```

Follow the prompts. Log in at `/accounts/login/` with this account to unlock
`/simulation/` and other controller tools.

The map consumes JSON APIs under `/api/*` (stations, routes, alerts, tickets, summary,
trains).

For the demo walkthrough script, see `demo_assets/demo_scenario.md`.

## 11. Development Workflow

After changing any model in `backend/railway/models.py`:

```bash
python manage.py makemigrations
python manage.py migrate
```

To reset demo data, rerun the seed commands (Step 8).

Useful checks:

```bash
python check_all_py.py             # AST syntax check of all .py files (repo root)
python backend/validate_api.py     # manual API URL checker
python backend/check_templates.py  # template validation helper
```

## 12. Troubleshooting

| Problem                                             | Fix                                                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `ImproperlyConfigured` / setup error about database | `DATABASE_URL` missing or set to SQLite — see Step 6                                       |
| Connection refused / timeout to Supabase            | Use the **Session pooler** URL (port 5432), not the direct connection (port 5432 IPv6)     |
| `ModuleNotFoundError: torch`                        | Run `pip install -r requirements.txt` inside the activated venv                            |
| Simulation page says scenarios are generic          | No LLM key configured — add one in `.env`, or rely on the built-in physics engine fallback |
| Port 8000 already in use                            | `python manage.py runserver 8080`                                                          |
| Map shows no routes                                 | Rerun `seed_routes`; route geometry comes from `TrackSection.geometry`                     |

## 13. Production Deployment

Set these environment variables on your hosting platform:

```env
DATABASE_URL=postgresql://...
SECRET_KEY=<strong-random-secret>
DEBUG=False
ALLOWED_HOSTS=your-domain.com
```

Then migrate and collect static files as usual. Never run production with `DEBUG=True`.
